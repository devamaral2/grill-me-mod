Build a personal to-do manager as an HTTP JSON API in TypeScript on Node.js, from scratch, in the current working directory (it starts empty). Your work will be checked against the numbered requirements below by external tests.

## Execution contract

The tests start the application with `npm install` followed by `npm start`, from the root of the current working directory. The application must listen on the port given by the `PORT` environment variable. It keeps all data in memory only: restarting it must give back an empty application.

## The todo resource

A todo has these fields, all returned in every response that returns a todo:

| field         | type                                   | notes                                           |
|---------------|----------------------------------------|-------------------------------------------------|
| `id`          | string                                 | UUID v4, generated by the server                |
| `title`       | string                                 | required, see R2                                |
| `description` | string or `null`                       | default `null`                                  |
| `status`      | `"todo"`, `"in_progress"` or `"done"`  | new todos start as `"todo"`                     |
| `tags`        | array of strings                       | default `[]`                                    |
| `dueDate`     | string `YYYY-MM-DD` or `null`          | default `null`                                  |
| `createdAt`   | string                                 | ISO 8601 UTC timestamp, set on creation         |
| `updatedAt`   | string                                 | ISO 8601 UTC timestamp, changes on every update |

All request and response bodies are JSON (`Content-Type: application/json`), except where a status code says the body is empty.

## Requirements

**R1. Create.** `POST /todos` with a JSON object body creates a todo and responds `201` with the todo. The body may contain `title`, `description`, `tags` and `dueDate`. Any other field in the body, including `id`, `status`, `createdAt` and `updatedAt`, is ignored. On creation `updatedAt` equals `createdAt`.

**R2. Create validation.** `POST /todos` responds `400` when: `title` is missing, is not a string, or is empty after trimming whitespace; `title` is longer than 120 characters after trimming; `description` is present, not `null`, and is not a string of at most 1000 characters; `tags` is present and is not an array of at most 10 strings, each non-empty after trimming and at most 30 characters, with no duplicates after trimming. The title and the tags are stored trimmed. A body that is not a JSON object also responds `400`.

**R3. Get one.** `GET /todos/{id}` responds `200` with the todo, or `404` when no todo has that id.

**R4. List.** `GET /todos` responds `200` with `{"items": [...], "total": N, "limit": L, "offset": O}`. Without query parameters the items are all todos in creation order (oldest first), `limit` is `20` and `offset` is `0`. `total` is the number of todos that match the filters, before pagination.

**R5. Filter by status.** `GET /todos?status={status}` returns only todos with that status. A `status` value that is not one of the three statuses responds `400`.

**R6. Filter by tag.** `GET /todos?tag={tag}` returns only todos whose `tags` contain exactly that tag (case-sensitive). When `status` and `tag` are both given, a todo must match both.

**R7. Sort.** `GET /todos?sort={field}&order={direction}` sorts the list. `field` is one of `createdAt`, `dueDate`, `title`; `direction` is `asc` or `desc`. `sort` defaults to `createdAt` and `order` defaults to `asc`. Todos with equal sort values keep their creation order. When sorting by `dueDate`, todos with a `null` `dueDate` always come last, in both directions. A value outside these sets responds `400`.

**R8. Pagination.** `GET /todos?limit={n}&offset={m}` returns the slice of the filtered and sorted list that starts at position `m` and has at most `n` items. `limit` is an integer from `1` to `100`; `offset` is an integer from `0` upward. A value outside these ranges, or not an integer, responds `400`. The `limit` and `offset` in the response are the values used.

**R9. Update.** `PATCH /todos/{id}` with a JSON object body updates only the fields present among `title`, `description`, `tags` and `dueDate`, responds `200` with the updated todo, and sets `updatedAt` to the time of the update. `description` and `dueDate` can be set to `null`. `tags`, when present, replaces the whole array. The validation rules of R2 and R12 apply to the fields present. A body with none of the four fields, or one that is not a JSON object, responds `400`. Other fields, including `status`, are ignored. An unknown id responds `404`.

**R10. Change status.** `PUT /todos/{id}/status` with body `{"status": "..."}` changes the status and responds `200` with the updated todo, with `updatedAt` updated. The allowed changes are `todo` to `in_progress`, `in_progress` to `todo`, `in_progress` to `done`, and `done` to `in_progress`. Any other change, including setting the current status again, responds `409`. A missing `status` or a value that is not one of the three statuses responds `400`. An unknown id responds `404`.

**R11. Delete.** `DELETE /todos/{id}` responds `204` with an empty body and removes the todo, so a later `GET /todos/{id}` responds `404`. An unknown id responds `404`.

**R12. Due date validation.** `dueDate`, when present and not `null`, must be a string in the exact format `YYYY-MM-DD` that is a real calendar date (`2025-02-30` and `2025-1-5` are invalid). An invalid value responds `400`, on both create and update. Dates in the past are valid.

**R13. Overdue.** `GET /todos/overdue` responds `200` with `{"items": [...], "total": N}`, where the items are the todos whose `dueDate` is earlier than today's date in UTC and whose `status` is not `done`, ordered by `dueDate` ascending, then by creation order. It takes no query parameters.

**R14. Health.** `GET /health` responds `200` with `{"status": "ok"}`.

**R15. Errors.** Every `4xx` response has the body `{"error": {"code": "...", "message": "..."}}`, where `message` is a non-empty string and `code` is `"validation_error"` for `400`, `"not_found"` for `404` and `"invalid_transition"` for `409`. A request to a route that does not exist, or with a method a route does not support, responds `404` with code `"not_found"`. A request body that is not valid JSON responds `400` with code `"validation_error"`. An id that is not a valid UUID is simply an unknown id: `404`.
